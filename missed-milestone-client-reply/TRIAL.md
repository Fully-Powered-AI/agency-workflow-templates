# Missed milestone client reply: tried once on its example

- **Product:** Claude, run in Claude Code
- **Model:** Claude Sonnet 5.5 (model ID claude-sonnet-5-5)
- **Date:** 2026-11-10

The inputs were the invented example in [example.md](example.md): the client message, milestone record, scope notes, approval history, statements record, delivery status, recovery options and reply settings for the invented Client K landing-page project, with today as Friday 16 October 2026. No client data was used. The assistant that ran the template did not write it. It followed the template's instruction block and output format on those inputs and did not read the example's published draft until its own was finished.

## What was observed

Every part the format asks for was produced: the draft reply, the seven checked points, the timeline with arithmetic, confirmed facts, proposed recovery steps, decisions needed, left open, before sending and the closing line. Nothing in the inputs made the template stop. Nothing was sent, offered or committed.

Where the instructions left room to guess:

- **A client sentence can hold several claims.** The rule is one label per claim. The run split the message into seven points. The published example uses six and does not make the 26 October launch its own point.
- **"Nothing has arrived."** The records show versions 2 and 3 were submitted, so the claim is Contradicted, but they do not say whether version 2 was meant as the final copy, and the delivery status has no row for the final-copy milestone.
- **A recovery option whose condition lies in the future.** The template offers an option only when its conditions hold on the facts supplied. "Copy approved by Monday 19 October" cannot yet hold. The run proposed it as conditional and flagged it. The template does not say which way to go.
- **"Within one working day of the request."** It is unclear whether this is a limit on the agency's response or a condition on the client's request. The run left it out of the reply; the published example states it.
- **The reply must not use the words credit, refund or discount unless the client did.** The client wrote "at no cost". The run treated it as a request about cost and said only that it is being considered by the person who decides. The instruction block, unlike the procedure, does not list the banned words or the "being considered" exception.
- **Who authorises credits is not an input,** so the Decides line for the cost decision names a role only.
- **Working days.** The settings say Monday to Friday and give no holiday list, so every weekday counted. The template does not say what to do about public holidays.
- **A deadline that falls on the day of sending.** The two-working-day feedback window on version 3 ends on the day of the reply. The procedure allows stating a client deadline backed by the scope notes, but does not say how to handle one that is already due. The run put the date in the reply and flagged it for the director.
- **Asking for feedback on version 3 may open a third round.** The scope notes say further rounds are quoted. The template has no step for this. The run listed it under Left open.
- **Contact name, subject and today's date.** The inputs give none of the contact's name or the email subject, so the run left them as decision gaps. Today's date appears only in the example's introduction, not as an input block.
- **Which pairs of dates get elapsed-day figures** is not specified. The run chose consecutive events and the key gaps.

Differences from the published example:

- The example's reply carries a subject line and states the call's one-working-day limit. The run left the subject as a gap.
- The example merges the round-2 position and the cost question into one decision. The run made them two, plus a fifth for the subject and name.
- The example leaves the date to ask the client for a response as a decision gap. The run stated 16 October (the SOW window) and Monday 19 October (the option's condition) in the reply, which is more specific and arguably more than the director has approved.
- The example's reply says version 2 went "a day ahead of the 9 October date". The run did not, to avoid suggesting the client is wrong.
- The example gives arithmetic for approval on 20 and 21 October as well; the run gave 16 and 19 October only.
- The example checks that version 3 reached the right contact and that the delivery director's agreement still stands. The run raised the first under Left open and the second only as a check on the option's condition.
- The labels for the claims both outputs share agree: Supported, Contradicted, Responsibility disputed, Records disagree, Request.
- The calendar and working-day figures agree: 7 and 5 days since 9 October, and Thursday 22 and Friday 23 October for approval on 16 and 19 October, both after the 21 October build date.

Facts in the outputs that are not in the inputs: the run's note says 12 October is a holiday in some places, which is outside knowledge and not something the records say; it should not have been added. The example's subject line "Landing-page copy and the 26 October launch" is invented wording, and its statement that the final copy "is not approved" is an inference from the approval history having no approval entry. Both outputs use the client's 26 October launch date, which only the client's message gives.

Against the reviewer checklist: the run's output traces each fact to a record, puts no future date outside a gap other than the feedback deadlines the SOW supports, recomputes every elapsed figure, proposes only authorised options, admits no fault, matches every gap in the reply to a decision, quotes both records where they disagree, and marks nothing as sent. One check is only partly met: the "Decisions needed" entry for the cost decision cannot name a decider from the inputs.

## Note added after the run

The template was revised after this run (version 0.1.1) in answer to the points above: options with a future condition are offered as conditional, the instruction block now says to use only supplied records and carries the rule on the words credit, refund and discount, claims inside one sentence are split, and the published example no longer sets version 2 beside the final-copy date, makes the 26 October launch its own point and gives today's date as its own input. The output recorded above is unchanged, and the revised template has not been run again.

A second review then found faults in the published example (the timeline lacked sources and calendar-day figures, and the response date was left as a gap although the scope notes support it), and the template was revised again (version 0.1.2: a stop check for threats before the first step, and a rule for a missing subject or contact name). The example now follows the revised template. This record still describes the first run on the earlier example and template wording, so comparisons above to "the published example" refer to the example as it then stood, not as it now reads. It has not been run again.

A third, smaller revision followed an independent review (version 0.1.3). It restated the default working-day counting rule in the instruction block, said that a future date needs a date in the delivery-confirmed cell, put the example's reply in the client's order with the second round, the build date and cost as separate decisions (four in all), and added the "does not shorten the four-day build" limit to the reply. The output recorded above is unchanged. The comparisons above to "the published example" still describe the example as it stood at the time of the run, and this run has not been repeated on the current template and example.
